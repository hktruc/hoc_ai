BÀI 14

Context Engineering

Bài giảng

Prompt engineering tập trung vào cách viết instruction. Context engineering rộng hơn: lựa chọn toàn bộ thông tin được đưa vào model tại mỗi lần inference — system instructions, tool descriptions, history, state, files, retrieval results và memory. Context là tài nguyên hữu hạn; nhiều hơn không đồng nghĩa tốt hơn.

Trong agent loop, dữ liệu tăng sau mỗi tool call. Nếu cứ nhét toàn bộ vào context, tín hiệu quan trọng bị loãng. Công việc của kiến trúc sư là quyết định thông tin nào cần hiện diện ngay bây giờ.

POSSIBLE INFORMATION ├ system rules ├ current goal ├ current state ├ relevant history ├ tool schemas ├ tool results ├ files / retrieval └ memory ↓ curate MODEL CONTEXT FOR THIS TURN

Bài tập

  1. Chọn 5 bước của Media Agent.
  2. Với từng bước, liệt kê “must see / nice to see / must not see”.
  3. Loại khỏi context những dữ liệu không phục vụ quyết định hiện tại.
  4. Ghi lý do từng dữ liệu được đưa vào.

Deliverable: Context Matrix 5 bước.

Nguồn

AEffective Context Engineering for AI Agents: context là tập token dùng trong inference; context engineering là quá trình curate và duy trì tập thông tin tối ưu.

BÀI 15

Context Window, Compaction và Retrieval

Bài giảng

Agent dài hạn sẽ tạo nhiều history hơn context window có thể chứa. Ngay cả khi model có context rất lớn, information relevance vẫn là vấn đề. Ba kỹ thuật thực dụng là: compaction — tóm lược trạng thái cũ; structured note-taking — lưu kết quả quan trọng ra ngoài context; và selective retrieval — chỉ lấy phần cần thiết khi cần.

Compaction tốt không chỉ tóm tắt hội thoại; nó phải giữ goal, quyết định đã chốt, constraints, artifacts, unresolved issues và next actions. Nếu mất những yếu tố này, agent “quên” dù summary vẫn đọc rất hay.

Thực hành

  1. Tạo một giả lập session 30 message với tool results dài.
  2. Thiết kế compaction schema gồm: goal, completed, decisions, constraints, artifacts, pending, next.
  3. Rút context xuống dưới 20% độ dài ban đầu.
  4. Kiểm tra agent có thể tiếp tục đúng từ summary hay không.

Nguồn

AContext Engineering: context pollution, compaction, structured note-taking và chiến lược cho long-horizon tasks.

AEffective Harnesses for Long-Running Agents: thách thức duy trì tiến độ qua nhiều context windows.

BÀI 16

State: sự thật vận hành của agent

Bài giảng

State trả lời câu hỏi: hệ thống đang ở đâu, đã làm gì, còn gì chưa làm và dữ liệu hiện tại là gì. State nên là dữ liệu có cấu trúc do application sở hữu, thay vì chỉ nằm ẩn trong lịch sử chat.

{
  "task_id":"media-042",
  "phase":"transcription",
  "input":"zoom.mp4",
  "artifacts":{"audio":"work/audio.wav"},
  "completed":["inspect_video","extract_audio"],
  "pending":["transcribe","summarize"],
  "attempts":{"transcribe":1}
}

State và context liên quan nhưng không đồng nhất. State có thể rất lớn; chỉ một phần state được project vào context cho model. State cũng cần schema/version nếu workflow thay đổi lâu dài.

Bài tập

  1. Thiết kế JSON state cho Mini project 3.
  2. Tách fields thành: identity, progress, artifacts, decisions, errors, metrics.
  3. Định nghĩa transition hợp lệ giữa 5 phases.
  4. Thêm rule chống chạy lặp một side effect đã thành công.

Nguồn

LLangGraph Quickstart: graph state lưu messages và dữ liệu xuyên suốt execution.

LLangGraph Persistence: state snapshots/checkpoints được lưu theo từng bước.

BIÊN SOẠNJSON schema mẫu và phân nhóm fields là đề xuất thực hành của giáo trình.

BÀI 17

Memory: nhớ cái gì, trong bao lâu, vì sao?

Bài giảng

“Memory” là thuật ngữ dễ bị dùng quá rộng. Trong thiết kế, nên hỏi cụ thể: dữ liệu này phục vụ turn hiện tại, session hiện tại hay nhiều session? Nó là factual memory, preference hay procedure? Ai được phép ghi, sửa và quên?

WORKING: dữ liệu cần cho bước hiện tại SESSION: dữ liệu của một task/conversation LONG-TERM: thông tin cần qua nhiều session SEMANTIC: facts/preferences có thể truy hồi PROCEDURAL: quy tắc/cách làm được duy trì

Không nên tự động ghi mọi thứ vào long-term memory. Memory sai hoặc cũ có thể phá agent lâu dài hơn một câu trả lời sai. Cần policy về write, confidence, expiry và user control.

Bài tập

  1. Liệt kê 20 dữ liệu mà Media Agent có thể gặp.
  2. Phân loại theo lifetime.
  3. Chỉ chọn tối đa 5 dữ liệu xứng đáng long-term.
  4. Viết memory write policy: điều kiện ghi, cập nhật, xóa.
  5. Viết 3 case memory conflict và cách giải quyết.

Nguồn

OOpenAI Agents SDK: Sessions cung cấp persistent memory layer để duy trì working context trong agent loop.

LLangGraph Persistence: checkpointing hỗ trợ memory giữa các interactions.

BIÊN SOẠNTaxonomy working/session/long-term/semantic/procedural được dùng ở đây như mô hình học, không phải taxonomy duy nhất của các framework.

BÀI 18

Filesystem as Memory và khả năng resume

Bài giảng

Với agent local chuyên biệt, filesystem thường là lớp persistence đầu tiên rất tốt vì dễ đọc bằng người, dễ backup, dễ version control và dễ debug. Không phải mọi bài toán memory đều cần vector database.

project/ ├─ project.md # mục tiêu + constraint ├─ state.json # trạng thái máy ├─ input/ ├─ work/ ├─ output/ ├─ notes/ │ └─ progress.md # handoff/compaction └─ logs/ └─ run-001.jsonl

State machine nên có atomic writes hoặc backup để tránh file state hỏng khi chương trình dừng giữa chừng. Artifact path nên tương đối trong workspace. Mỗi side effect quan trọng nên có idempotency key hoặc completed marker.

Mini project 4 — Resume Agent

  1. Tạo cấu trúc folder trên.
  2. Viết script xử lý 5 bước, mỗi bước cập nhật state.json.
  3. Cố tình dừng chương trình ở bước 3.
  4. Chạy lại và đảm bảo bước 1–2 không bị làm lại nếu đã hoàn thành.
  5. Thêm progress.md tóm tắt cho một model mới tiếp tục.
  6. Ghi log mọi transition và error.

Deliverable: repo chạy được + video/screenshot chứng minh resume.

Nguồn

AEffective Harnesses for Long-Running Agents: dùng artifacts/progress để bridge các session và context windows.

LLangGraph Persistence: checkpoints hỗ trợ resume, fault tolerance và time travel.

BIÊN SOẠNFilesystem layout là pattern đề xuất dành cho agent local của giáo trình.
