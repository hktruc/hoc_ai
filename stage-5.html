Agent Loop

Từ đây hệ thống bắt đầu có quyền tự chọn bước tiếp theo. Vì vậy planning, stopping và recovery phải được thiết kế như first-class components.

BÀI 19

ReAct: Reason → Act → Observe

Bài giảng

Trong một agent loop thực dụng, model luân phiên giữa việc quyết định hành động và quan sát kết quả thực tế. Ta không cần phụ thuộc vào việc hiển thị chain-of-thought; thứ cần log và kiểm soát là các hành động bên ngoài: tool selected, arguments, result, state transition.

GOAL ↓ DECIDE NEXT ACTION ↓ TOOL CALL ↓ OBSERVATION ↓ UPDATE STATE ↓ complete? ─ no ─→ DECIDE NEXT ACTION │yes ↓ FINAL

Điểm mạnh của loop này là agent có thể thay đổi kế hoạch khi môi trường trả kết quả khác dự kiến. Điểm yếu là trajectory khó dự đoán. Vì vậy tool surface, budget và stop rules phải rõ.

Bài tập

  1. Viết một agent loop tối thiểu bằng pseudocode hoặc Python.
  2. Cho agent 3 tools: inspect, transcribe, summarize.
  3. Log mỗi turn: available tools, chosen tool, result, state, reason code ngắn như need_metadata.
  4. Tạo một case tool thất bại để quan sát trajectory.

Deliverable: trace của 3 runs, không cần lưu reasoning nội bộ.

Nguồn

OOpenAI Agents SDK: built-in agent loop quản lý turns và tool execution.

OTracing: trace ghi LLM generations, tool calls, handoffs, guardrails và events.

BÀI 20

Planning: plan-first hay dynamic?

Bài giảng

Plan-first tạo kế hoạch trước rồi thi hành; phù hợp khi task có cấu trúc khá rõ và cần user duyệt. Dynamic planning chọn hành động tiếp theo dựa trên observation mới; phù hợp khi môi trường khó dự đoán. Hệ thống production thường dùng hybrid: lập outline cấp cao trước nhưng cho phép replanning trong giới hạn.

PLAN-FIRST: Goal → Plan → Execute → Verify DYNAMIC: Goal → Act → Observe → Replan → Act ... HYBRID: Goal → Milestones → dynamic steps inside each milestone

Kế hoạch không nên là văn bản dài mang tính trang trí. Nó phải chuyển thành state có thể theo dõi: milestones, dependencies, status, acceptance criteria.

Bài tập

  1. Chọn task “tạo 3 Shorts từ video dài”.
  2. Thiết kế plan-first với milestones rõ.
  3. Thiết kế dynamic version cho trường hợp transcript lỗi hoặc không có đoạn đủ hay.
  4. Viết replanning trigger cụ thể.
  5. So sánh cost, latency, khả năng kiểm soát.

Nguồn

ABuilding Effective Agents: agents tự điều khiển quy trình và tool use dựa trên feedback môi trường.

BIÊN SOẠNPhân loại plan-first/dynamic/hybrid và milestone schema là cách tổ chức của giáo trình.

BÀI 21

Stopping Conditions và Budget

Bài giảng

Agent không nên chỉ dừng khi “model thấy xong”. Runtime cần các hard limits độc lập: max turns, timeout, token/cost budget, retry limit, allowed side effects và human-required state. Đồng thời cần completion criteria thuộc domain.

STOP IF ANY: ✓ acceptance criteria satisfied ✓ final artifact exists + validates ✕ max_turns reached ✕ max_cost reached ✕ timeout ✕ repeated_failure >= N ! human_approval_required

Mỗi stop reason phải được log. Khi chạm hard limit, hệ thống nên trả partial state và next action rõ để có thể resume, thay vì chỉ “Agent failed”.

Bài tập

  1. Định nghĩa 5 hard stops và 5 domain completion checks cho Media Agent.
  2. Thiết kế output khi stop do budget.
  3. Thử một loop cố tình không thể hoàn thành; kiểm tra nó dừng an toàn.
  4. Đo số turn trung bình trên 10 test cases.

Nguồn

OOpenAI Tracing: trace/turn spans hỗ trợ theo dõi số turn và token usage.

BIÊN SOẠNBộ stop rules và budget envelope là practice kiến trúc của giáo trình, tổng hợp từ defensive software engineering.

BÀI 22

Error Recovery: retry không phải chiến lược duy nhất

Bài giảng

Phân loại error trước khi xử lý. Transient như timeout/rate limit có thể retry với backoff. Deterministic như file không tồn tại thì retry y hệt vô ích. Semantic failure như output không đạt rubric cần đổi prompt/plan. Permission failure phải xin quyền hoặc dừng.

ERROR ├─ transient → retry/backoff ├─ invalid input → repair/ask user ├─ tool unavailable → alternate tool ├─ semantic quality → evaluator → revise ├─ permission → human approval └─ unsafe/unknown → stop + preserve state

Side effects phải idempotent hoặc có cơ chế kiểm tra trước retry. Ví dụ upload video thành công nhưng response timeout: retry mù có thể upload trùng. Cần idempotency key hoặc “check-before-create”.

Bài tập

  1. Tạo Error Taxonomy tối thiểu 12 lỗi cho Media Agent.
  2. Mỗi lỗi ghi retryable?, max attempts, fallback, state impact.
  3. Mô phỏng 4 lỗi: API 429, missing file, invalid JSON, upload timeout.
  4. Kiểm tra hệ thống không tạo duplicate side effect.

Deliverable: recovery policy + test logs.

Nguồn

LLangGraph Persistence: checkpoints hỗ trợ fault-tolerant execution và resume từ bước thành công gần nhất.

LThinking in LangGraph: ví dụ node có retry policy cho transient failures.

BIÊN SOẠNError taxonomy và idempotency exercise là phần software reliability được áp vào agent systems.
