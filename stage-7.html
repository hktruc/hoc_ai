BÀI 27

Chọn framework: raw API, Agents SDK, LangGraph hay ADK?

Bài giảng

Không có framework “tốt nhất” độc lập với bài toán. Hãy chọn theo thứ bạn muốn framework sở hữu. Nếu bạn muốn tự nắm loop, tool dispatch và state, raw model API cho độ minh bạch cao. Nếu muốn runtime quản lý turns, tools, guardrails, sessions và handoffs, Agents SDK giảm boilerplate. Nếu workflow là graph stateful với checkpoints, interrupts và resume, LangGraph mạnh ở orchestration/persistence. Google ADK cung cấp hệ sinh thái code-first cho agents, tools, sessions/evals và deployment trên Google Cloud.

NEED MINIMAL CONTROL / LEARN CORE → Python + raw API NEED agent runtime + tools + guardrails + tracing → OpenAI Agents SDK NEED explicit state graph + checkpoints + interrupts → LangGraph NEED Google agent ecosystem / ADK lifecycle → Google ADK

Đây không phải thứ tự bắt buộc hay ranking chất lượng. Đây là roadmap học: tự xây loop nhỏ trước để hiểu cơ chế, rồi dùng framework để giảm code mà bạn đã hiểu.

Thực hành

  1. Lấy Mini project 3 hoặc 4.
  2. Liệt kê những thứ bạn đang tự code: loop, tool schema, state, checkpoint, tracing, approval.
  3. Chọn một framework và map từng responsibility sang framework feature.
  4. Port một flow nhỏ, không port toàn dự án.
  5. So sánh: lines of code, transparency, debug, lock-in, deployment.

Deliverable: Framework Decision Record (ADR) 1–2 trang, có lý do chọn và lý do không chọn các phương án còn lại.

Nguồn

OOpenAI Agents SDK: mô tả khi dùng Responses API trực tiếp và khi dùng Agents SDK; primitives gồm agents, handoffs/agents-as-tools, guardrails, sessions, HITL, tracing.

LLangGraph Persistence: checkpoints, threads, memory, time travel và fault tolerance.

GGoogle ADK — Coding with AI: lifecycle scaffold, build, test, evaluate và deploy; docs index/MCP.

BIÊN SOẠNBảng lựa chọn framework là heuristic của giáo trình, không phải tuyên bố chính thức của các hãng.

BÀI 28

Multi-Agent: chỉ dùng khi decomposition thật sự cần autonomy

Bài giảng

Multi-agent tăng khả năng specialization nhưng cũng tăng context handoff, latency, cost, eval surface và failure modes. Trước khi tạo agent thứ hai, hỏi: nhiệm vụ này có thể là tool/function không? Có cần persona/context/toolset riêng? Có cần agent đó tự chạy loop độc lập không?

Hai pattern phổ biến là manager — agent trung tâm giữ quyền điều phối và gọi specialist như tools; và handoff — chuyển quyền xử lý sang specialist. Manager dễ tập trung policy; handoff giúp specialist sở hữu conversation/task riêng.

SINGLE AGENT + TOOLS ưu tiên nếu đủ MANAGER ├ specialist as tool ├ specialist as tool └ manager owns final answer HANDOFF triage agent → specialist owns next interaction

Một worker đơn giản không nhất thiết là agent. Nếu nó chỉ nhận input và trả output trong một bước, function/LLM call chuyên biệt thường dễ quản lý hơn.

Bài tập

  1. Vẽ Media Agent single-agent + tools.
  2. Vẽ bản multi-agent: Planner, Media Worker, Content Worker, Reviewer.
  3. Với từng agent, ghi lý do tại sao không thể là tool/function.
  4. Nếu không có lý do mạnh, gộp lại.
  5. Thiết kế handoff contract: input, context được truyền, expected output, ownership.
  6. Chạy cùng 10 test cases trên 2 kiến trúc và so sánh success/cost/latency.

Deliverable: Multi-Agent Justification Report. Mục tiêu không phải chứng minh multi-agent tốt hơn; mục tiêu là biết khi nào nó đáng giá.

Nguồn

OOpenAI Agents SDK — Agents: manager (agents as tools) và handoffs là các composition patterns.

ABuilding Effective Agents: khuyến nghị dùng patterns đơn giản, composable và chỉ tăng complexity khi cải thiện outcome.

CAPSTONE

Dự án cuối khóa — Local AI Media Agent

Xây một agent local có thể nhận video/audio/image/text instruction, lập kế hoạch, dùng tool, lưu state, tự kiểm tra và xin phép trước side effects quan trọng.

Use case chuẩn

User: “Hãy lấy video Zoom này, bỏ 3 phút đầu, phát hiện các khoảng im lặng dài, tạo transcript, viết mô tả YouTube, xuất video 1080p và chuẩn bị thumbnail. Trước khi upload hoặc ghi đè file, phải hỏi tôi.”

Kiến trúc mục tiêu

USER / CLI or WEB UI ↓ TASK INTAKE + VALIDATION ↓ PLANNER / ROUTER ↓ STATE MACHINE ───────────────┐ ↓ │ TOOL LAYER │ ├ filesystem.* │ ├ media.* (FFmpeg/FFprobe) │ ├ speech.* │ ├ vision.* │ └ content.* │ ↓ │ OBSERVATIONS → EVALUATOR ────┘ retry/replan ↓ HUMAN APPROVAL for risky side effects ↓ ARTIFACTS + REPORT + TRACE

Yêu cầu bắt buộc

A. Architecture

  • Goal/task decomposition.
  • Deterministic vs AI matrix.
  • State schema và transitions.
  • Tool catalog + permission matrix.
  • Stopping/recovery policy.

B. Runtime

  • Chạy local.
  • Workspace riêng cho mỗi task.
  • Resume sau restart.
  • Structured logs/traces.
  • Config/API keys tách khỏi code.

C. AI

  • Ít nhất một router/planner.
  • Ít nhất một evaluation step.
  • Structured outputs.
  • Không dùng LLM cho việc deterministic đã có code tốt.

D. Safety

  • Không delete mặc định.
  • Không ghi ngoài workspace.
  • Approval trước upload/publish/overwrite.
  • Timeout + max turns + retry limits.

Milestones thực hiện

  1. M0 — Spec: viết problem statement, success criteria, non-goals.
  2. M1 — Deterministic core: FFmpeg/FFprobe tools chạy và test độc lập.
  3. M2 — LLM tool loop: model chọn read-only tools và tạo plan.
  4. M3 — State & resume: state.json/checkpoint, restart không mất tiến độ.
  5. M4 — Write tools: edit/render trong workspace, idempotency.
  6. M5 — Evaluator: validate artifact + content rubric + retry cap.
  7. M6 — HITL: approval cho overwrite/upload.
  8. M7 — Eval suite: tối thiểu 30 cases và baseline report.
  9. M8 — Framework optional: port sang Agents SDK/LangGraph/ADK nếu đem lại lợi ích rõ.
  10. M9 — Demo: quay video 5–10 phút từ input đến output và giải thích kiến trúc.
