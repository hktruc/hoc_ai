CHẶNG 02 • BÀI 5–9

Workflow Design

Học 5 pattern cốt lõi để biến một bài toán lớn thành hệ thống có thể kiểm soát, đánh giá và mở rộng.

BÀI 05

Prompt Chaining

Bài giảng

Prompt chaining chia một nhiệm vụ thành chuỗi bước mà output bước trước trở thành input bước sau. Pattern này phù hợp khi ta biết trước các bước và mỗi bước có thể được tối ưu riêng. Thay vì yêu cầu một model “vừa làm sạch transcript, vừa tóm tắt, vừa viết mô tả YouTube”, ta tách thành các nhiệm vụ nhỏ hơn.

RAW TRANSCRIPT → CLEAN → STRUCTURE → SUMMARY → YOUTUBE DESCRIPTION

Ưu điểm là dễ debug: nếu mô tả YouTube tệ, ta kiểm tra xem lỗi bắt đầu từ transcript sạch, cấu trúc hay bước viết cuối. Nhược điểm là latency tăng và lỗi ở bước đầu có thể lan xuống cuối. Vì vậy nên đặt validation gate tại các điểm quan trọng.

Thực hành

  1. Lấy một transcript thật dài 3–10 phút.
  2. Thiết kế 4 prompt riêng: clean, extract outline, summarize, write description.
  3. Định nghĩa output schema của từng bước.
  4. Thêm gate sau bước clean: nếu transcript quá ngắn hoặc mất đoạn, dừng.
  5. So sánh với một prompt “làm tất cả”.

Deliverable: sơ đồ pipeline + 4 prompt + schema + bảng so sánh chất lượng/latency.

BÀI 06

Routing

Bài giảng

Routing phân loại input rồi chuyển sang nhánh chuyên biệt. Giá trị lớn nhất của routing là tách concern: mỗi loại yêu cầu có prompt, tool và policy riêng thay vì ép một prompt khổng lồ xử lý tất cả.

INPUT ↓ ROUTER ├─ transcript → text pipeline ├─ image → vision pipeline ├─ video → media pipeline └─ unknown → ask user / fallback

Router có thể là rule-based, classifier nhỏ hoặc LLM. Nếu phân loại dựa trên extension file thì không cần LLM. Nếu dựa trên ý định ngôn ngữ mơ hồ, LLM có thể phù hợp hơn. Luôn có fallback cho low confidence.

Thực hành

  1. Viết 20 yêu cầu người dùng cho Media Agent.
  2. Tạo taxonomy 4–8 intent.
  3. Định nghĩa route, confidence và fallback.
  4. Viết 5 case cố tình mơ hồ.
  5. Đánh giá: route đúng bao nhiêu/20?

Deliverable: intent taxonomy + router prompt/rules + confusion cases.

Nguồn

BÀI 07

Parallelization

Bài giảng

Khi các subtasks độc lập, chạy tuần tự làm tăng latency không cần thiết. Parallelization thường có hai dạng: sectioning — tách một bài toán thành các phần độc lập; và voting — chạy nhiều lượt để có đa góc nhìn rồi tổng hợp.

VIDEO INPUT ├─ transcribe audio ─┐ ├─ detect scenes ────┼→ AGGREGATOR └─ extract metadata ─┘

Không song song hóa nếu B phụ thuộc output của A. Đồng thời phải nghĩ đến rate limit, cost và cách aggregate khi một nhánh fail.

Thực hành

  1. Vẽ dependency graph cho quy trình video.
  2. Tô màu các node có thể chạy song song.
  3. Thiết kế timeout và fallback cho từng branch.
  4. Tính thời gian lý thuyết tuần tự và song song.

Deliverable: DAG đơn giản + bảng dependency + timeout policy.

Nguồn

ABuilding Effective Agents: parallelization gồm sectioning và voting.

BÀI 08

Orchestrator–Worker

Bài giảng

Pattern này phù hợp khi không thể định trước hoàn toàn số lượng hay loại subtasks. Orchestrator phân tích mục tiêu, tạo subtasks, giao cho workers rồi tổng hợp. Đây khác parallelization cố định ở chỗ việc phân rã được quyết định động.

GOAL ↓ ORCHESTRATOR ├─ Worker: research ├─ Worker: edit ├─ Worker: verify └─ Worker: format ↓ SYNTHESIS

Worker không nhất thiết là agent độc lập; nhiều trường hợp worker chỉ là một function hoặc một LLM call chuyên biệt. Càng nhiều autonomous workers, càng khó quan sát và eval.

Thực hành

  1. Chọn task “tạo bộ nội dung từ một video dài”.
  2. Thiết kế orchestrator output dưới dạng danh sách jobs.
  3. Mỗi job phải có goal, input, expected output và acceptance criteria.
  4. Thiết kế aggregator xử lý khi một worker fail.
  5. So sánh với workflow cố định: khi nào orchestrator thật sự cần thiết?

BÀI 09

Evaluator–Optimizer

Bài giảng

Evaluator–optimizer dùng một vòng phản hồi có tiêu chí rõ: generator tạo kết quả, evaluator đánh giá, optimizer sửa theo feedback. Pattern này đáng dùng khi chất lượng có thể mô tả bằng rubric và iteration tạo giá trị.

GENERATE → EVALUATE │ pass? yes → OUTPUT │ no ↓ IMPROVE ─────┐ └─────────┘

Nếu evaluator chỉ nói “chưa hay, làm lại”, loop dễ vô hạn. Rubric cần cụ thể: đủ nội dung, đúng tone, không bịa, độ dài, cấu trúc, constraint. Đồng thời cần max iterations.

Mini project 2

Workflow: Transcript Zoom → clean → outline → summary → YouTube description → evaluator.

  1. Viết acceptance criteria cho từng bước.
  2. Chọn 2 bước có evaluator.
  3. Định nghĩa score 0–2 cho từng tiêu chí.
  4. Nếu tổng dưới ngưỡng, optimizer nhận feedback có cấu trúc và sửa tối đa 2 lần.
  5. Chạy 3 transcript khác nhau và lưu log.

Deliverable: workflow spec + rubric + 3 execution logs.
