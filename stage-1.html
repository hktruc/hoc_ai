BÀI 01

AI Agent không phải chatbot

Câu hỏi thiết kế: Bài toán của tôi có thật sự cần quyền tự quyết của model hay chỉ cần một workflow cố định?

Mục tiêu học

  • Phân biệt chatbot, LLM application, workflow và agent.
  • Nhận diện dấu hiệu “agent hóa quá mức”.
  • Viết được tiêu chí quyết định khi nào nên dùng workflow, khi nào nên dùng agent.

Bài giảng

Một chatbot đơn giản chủ yếu nhận input và sinh output. Một ứng dụng LLM có thể bổ sung retrieval, structured output hoặc tool calling nhưng vẫn chưa nhất thiết là agent. Điểm phân biệt hữu ích trong thiết kế là ai kiểm soát đường đi: nếu code định trước các bước và thứ tự, đó là workflow; nếu model được phép quyết định bước tiếp theo dựa trên trạng thái và kết quả tool, hệ thống mang tính agentic cao hơn.

Anthropic đề xuất ưu tiên giải pháp đơn giản nhất có thể và chỉ tăng mức tự trị khi sự linh hoạt thực sự tạo giá trị. Agent phù hợp khi số bước khó biết trước, cần thích nghi với kết quả trung gian, hoặc cần lựa chọn tool/chiến lược động. Ngược lại, nếu quy trình đã rõ và ổn định, workflow thường dễ kiểm thử, dễ dự đoán chi phí và ít lỗi hơn.

Chatbot → LLM App → Workflow → Agent → Multi-Agent Mức tự trị tăng dần → Độ khó kiểm soát, đánh giá và debug cũng tăng dần →

Ví dụ

Auto upload Zoom recording lên YouTube private: nếu luôn là “phát hiện file → đổi tên → upload → đặt private → lưu log”, không cần agent. AI xử lý video theo lệnh tự do: nếu người dùng có thể nói “hãy tìm 5 đoạn hay nhất, cắt thành Shorts, đoạn nào thiếu ngữ cảnh thì bỏ”, model phải phân tích và quyết định; đây là ứng viên tốt hơn cho agent.

Bài tập thực hành

  1. Liệt kê 10 automation hoặc ứng dụng AI bạn muốn xây.
  2. Với mỗi hệ thống, ghi: đường đi có biết trước không; số bước có cố định không; có cần model chọn tool không; sai một bước gây hậu quả gì.
  3. Gắn nhãn: Automation / Workflow / Agent.
  4. Chọn 2 mục bạn đang định làm agent và thử thiết kế lại thành workflow. Nếu workflow đủ dùng, ghi lý do không cần agent.

Sản phẩm phải nộp: bảng 10 dòng + đoạn kết luận 200–300 chữ “Khi nào tôi sẽ không dùng agent”.

BÀI 02

Goal → Task → Subtask → Action → Tool

Câu hỏi thiết kế: Tôi đang giải quyết mục tiêu hay đang ghép tool vì thấy chúng thú vị?

Mục tiêu học

  • Phân rã một mục tiêu kinh doanh thành hành vi có thể thực thi.
  • Tách “mục tiêu” khỏi “công nghệ”.
  • Chỉ chọn tool sau khi action đã rõ.

Bài giảng

Agent tốt bắt đầu từ mô hình công việc, không bắt đầu từ danh sách API. Một mục tiêu như “tạo video hoàn chỉnh” quá rộng để model xử lý đáng tin cậy. Ta cần tách thành task, subtask và action. Chỉ ở tầng action mới map sang tool cụ thể.

GOAL: Xuất video Zoom hoàn chỉnh ↓ TASK: Chuẩn bị nội dung ↓ SUBTASK: Tạo transcript ↓ ACTION: Tách audio → nhận dạng giọng nói ↓ TOOL: FFmpeg → Speech-to-text API

Điểm quan trọng là cùng một action có thể dùng nhiều tool khác nhau. Nếu thiết kế bắt đầu từ tool, kiến trúc bị khóa vào công nghệ. Nếu bắt đầu từ action, bạn có thể thay FFmpeg, API hay model mà không phá toàn bộ logic.

Bài tập thực hành

Chọn một quy trình thật, ví dụ “xử lý cloud recording Zoom thành nội dung YouTube”. Vẽ cây 5 tầng:

  1. 1 Goal.
  2. 3–7 Task.
  3. Mỗi task có 2–5 Subtask.
  4. Mỗi subtask có action cụ thể.
  5. Cuối cùng mới gắn tool khả thi.

Đánh dấu mỗi action bằng D (deterministic), AI (cần suy luận), H (cần con người). Chưa chọn framework.

Sản phẩm phải nộp: một cây công việc hoàn chỉnh, tối thiểu 20 action.

BÀI 03

Deterministic vs Probabilistic

Câu hỏi thiết kế: Việc nào phải chắc chắn bằng code, việc nào xứng đáng giao cho LLM?

Bài giảng

LLM là thành phần xác suất: cùng một input có thể tạo ra cách diễn giải hoặc quyết định khác nhau. Điều này hữu ích cho ngôn ngữ, phân loại mềm, lập kế hoạch và đánh giá ngữ nghĩa; nhưng không nên thay thế những thao tác máy tính vốn đã có thuật toán chính xác.

Ví dụ: đọc metadata video nên dùng FFprobe; resize nên dùng FFmpeg; kiểm tra file tồn tại nên dùng filesystem API. Dùng LLM cho các thao tác này làm tăng token, latency và thêm điểm lỗi. LLM nên đứng ở nơi cần judgment: đoạn nào đáng giữ, yêu cầu người dùng thuộc intent nào, plan nào phù hợp, output có đáp ứng mục tiêu hay chưa.

Nếu có thể viết rule chính xác + ổn định → CODE Nếu cần hiểu nghĩa / đánh giá / thích nghi → LLM Nếu hậu quả cao + khó đảo ngược → HUMAN APPROVAL

Bài tập thực hành

  1. Lấy cây công việc bài 2.
  2. Với từng action, hỏi: “Có thể giải bằng rule/code chính xác không?”
  3. Nếu có, chuyển về code.
  4. Nếu dùng AI, viết rõ lý do: semantic understanding, classification, planning, generation hay evaluation.
  5. Tính “AI surface”: số action AI / tổng số action. Thử giảm tỷ lệ này mà vẫn đạt mục tiêu.

Thử thách: thiết kế hai phiên bản cùng một hệ thống: V1 ít AI nhất và V2 agentic hơn. So sánh độ ổn định, chi phí, khả năng thích nghi.

BÀI 04

Kiến trúc cơ bản và Agent Loop

Câu hỏi thiết kế: Agent quan sát gì, quyết định gì, hành động bằng gì và dừng bằng điều kiện nào?

Bài giảng

Một agent tối thiểu cần model, instructions, tools và một runtime loop. Model nhận context hiện tại, có thể trả lời hoặc yêu cầu tool. Runtime thực thi tool, đưa observation trở lại model, rồi lặp cho đến khi có final output hoặc chạm điều kiện dừng.

USER GOAL ↓ CONTEXT + STATE ↓ MODEL DECISION ──→ FINAL ANSWER │ └─→ TOOL CALL → ENVIRONMENT → TOOL RESULT ↑ │ └─────────────────┘ vòng lặp

Đừng đồng nhất “reasoning” với việc phải lưu hay hiển thị suy nghĩ nội bộ. Về mặt kiến trúc, điều bạn cần quan sát được là quyết định công khai: tool nào được chọn, arguments gì, kết quả tool là gì, state thay đổi ra sao, vòng lặp kết thúc vì lý do nào.

Mini project 1 — Agent sắp xếp Downloads

  1. Định nghĩa goal: sắp xếp file nhưng không làm mất dữ liệu.
  2. Observation: danh sách file, extension, size, modified time.
  3. Tools: list_files, create_folder, move_file; tuyệt đối chưa có delete.
  4. Model decision: phân loại file vào nhóm.
  5. State: file nào đã xử lý, file nào chưa chắc chắn.
  6. Stopping: tất cả file được xử lý hoặc chuyển vào “Needs Review”.
  7. Vẽ sequence cho 3 file khác nhau, trong đó có 1 file mơ hồ.

Sản phẩm phải nộp: sơ đồ kiến trúc + tool list + state schema + stopping rules. Chưa cần code.
